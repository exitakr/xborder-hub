## 1. eBay Marketplace Insights API — ✗ 前提が崩れた

**仕様書の想定**（SPEC §3.2 Layer 1）
> Marketplace Insights API: 過去の落札実績を取得 §要検証
> このAPIは申請・承認が必要な可能性が高い。

**調査結果**

このAPIは **Limited Release** であり、eBay 公式ドキュメントは
「Order API / Offer API / Marketplace Insights API へのアクセスは
**申請しても付与されない**（cannot be granted upon request）」と明記している。
Application Growth Check を通しても対象外。
2026年6月時点の開発者コミュニティでも「主要パートナー以外には提供されていない」と
報告されている。Sandbox で動作しても Production では取得できない。

**影響**

「落札実績（実際に売れた価格）」を合法的に自動取得する手段が、MVP の予算・
体制では **存在しない**。これはデータソース設計の中核に関わる。

**採用した設計変更**

仕様書 §3.2 が用意していたフォールバックをそのまま採用した:

- Layer 1 は **Browse API（出品価格）のみ**とする
- 取得値は「現在の出品価格の外れ値除去済み中央値」であり、**落札価格ではない**
- 出品価格は落札価格より **高く出る**。この事実を UI と利用規約に明記する
  （`app/legal/terms` §3、銘柄詳細画面の出典欄）
- `price_snapshots.source` に `ebay_browse` を記録し、将来 Insights が
  取得可能になった場合に系列を区別できるようにした
- 変更が必要なのは `lib/ebay.ts` の `fetchPrice` 1 関数のみ

**買い手（買収検討者）への説明**

この制約は競合他社にも等しくかかる。だからこそ SPEC §3.2 Layer 3
（ユーザー投稿の取引実績）が最終的な差別化要因になる。実際に売れた価格を
持っているのは、ユーザーが自分で入力したアプリだけになる。
MVP では蓄積のみ行い価格表示には使わない方針を維持している
（`transactions` テーブルに実売価格が貯まり続ける設計）。

## 2. Vercel Cron 無料枠 — ✓ 前提は成立

| 項目 | 現行仕様 |
|---|---|
| Hobby プランの実行頻度 | **1日1回のみ** |
| ジョブ数 | 1プロジェクトあたり100 |
| 時刻精度 | **時間単位でのみ保証**（1:00 指定なら 1:00〜2:00 の間に発火） |
| タイムゾーン | **UTC のみ** |
| 1日1回を超える式 | **デプロイ時にエラー**になる |

発火が1時間ずれうる点は、日次スナップショットの設計上問題にならない。

Pro（$20/月）にすると分単位まで可能。日中の価格更新が必要になった段階で検討。

## 3. Supabase 無料枠 — ✓ 成立。ただし本番運用には注意点が1つ

| 項目 | 無料枠 |
|---|---|
| DB 容量 | 500 MB |
| ファイルストレージ | 1 GB |
| 月間アクティブユーザー | 50,000 |
| プロジェクト数 | 2 |
| **7日間アクセスがないとプロジェクトが一時停止** | ⚠️ |

**容量の見積もり**

`price_snapshots` が最も増える。1銘柄1日1行 × 60銘柄 = 年間約 21,900 行。
1行あたり100バイト未満なので年間 2 MB 程度。500 MB は当面問題にならない。

画像は長辺1024px / JPEG 品質0.8 で約150KB。1GB ≒ 約6,600枚 ≒
1人10点として約660人。**ここが最初に埋まる。** Pro（$25/月）で 100 GB。

**⚠️ 7日間の自動一時停止**

無料枠のまま公開すると、アクセスが途切れた週にプロジェクトが停止し、
Cron も 500 を返し続ける。**公開と同時に Pro への移行を推奨**。
売却を視野に入れるなら、稼働率の断絶は DD で必ず指摘される。

## 7. 価格ソースの追加調査（2026-08-02）

「Browse API 以外に無料で使えるものがあれば採用」という指示を受けての追加調査。
**2つ見つかり、いずれも採用しました。**どちらも Browse API より品質が高い（出品価格
ではなく**市場価格**を返す）ため、該当カテゴリは移行しています。

### 7.1 Scryfall（Magic: The Gathering）— 採用

| 項目 | 内容 |
|---|---|
| 認証 | 不要・完全無料 |
| 価格 | USD / EUR の**市場価格**（出品価格ではない） |
| 更新頻度 | **1日1回**（本アプリの日次 Cron と完全に一致） |
| レート制限 | 10 req/秒未満（本アプリは 1 req/秒） |
| 義務 | User-Agent の明示、**出典表示**、大量取得時は bulk data を使う |

⚠️ **収益化に直結する制約**：Scryfall のデータは
**「ペイウォールの背後に置いてはならない」**と規約に明記されています。
将来サブスクリプションを導入する場合、**MTG の価格は無料プランでも見られる必要**が
あります。売却時のデューデリジェンスで論点になりうるため、
`lib/sources/scryfall.ts` の冒頭にも同じ注意を書いています。

また「単に再配布・プロキシするだけでなく、付加価値を提供すること」も条件です。
本アプリはポートフォリオ管理という付加価値があるため要件を満たします。

### 7.2 Pokémon TCG API（pokemontcg.io）— 採用

| 項目 | 内容 |
|---|---|
| 認証 | 任意（API キーがあると日次上限が大幅に増える） |
| 価格 | TCGplayer（USD）と Cardmarket（EUR）の**市場価格** |
| 実装 | `POKEMONTCG_API_KEY` を設定すれば自動で使用 |

⚠️ 検索クエリは**必ず絞り込む**こと。カード名だけで検索すると再版（reprint）が
混ざり、価格が桁違いになります。マイグレーション 0005 で Base Set のカードには
`set.id:base1` を付けています。

### 7.2.1 価格「履歴」の調査（2026-08-03）— チャートが空になる問題

`price_snapshots` は Cron が1日1点ずつ積み上げるテーブルです。したがって
**カタログを投入した直後は履歴が0件で、グラフに何も描けません。**
「銘柄を追加してもグラフが出ない」のはこれが原因で、バグではなく設計上の帰結です。
とはいえ数週間待たないとグラフにならないのは製品として成立しないため、
**無料かつ商用利用可能な範囲で履歴を遡れるソースを再調査しました。**

| ソース | 履歴 | 判定 |
|---|---|---|
| **pokemontcg.io の Cardmarket** | `avg1` / `avg7` / `avg30`（移動平均） | ✅ **採用** |
| pokemontcg.io の TCGplayer | なし（現在値のみ） | 現在値のフォールバックとしてのみ使用 |
| Scryfall | なし | MTG の履歴は前進蓄積のみ |
| MTGJSON `AllPrices.json` | 90日分あり | ❌ 数 GB のバルク配布。Vercel の 60 秒・メモリ制限では処理不可 |
| JustTCG | 7d〜1y あり | ❌ **無料枠は非商用限定**。アプリ公開は商用のため使用不可 |
| 時計 / バッグ / スニーカー | — | ❌ 無料の履歴ソースなし |

**採用したのは Pokémon の Cardmarket 移動平均のみです。** 実装上、次の2点を守っています。

1. **移動平均は「その時点の価格」ではない。**
   `avg30` は直近30日の平均なので、指すのは**期間の中央（15日前）**であって30日前ではありません。
   よって各点は**窓の中点**に打刻しています（`avg7`→3.5日前、`avg30`→15日前）。
   窓の端に置くと「いつその価格だったか」を誤って伝えることになります。
2. **系列内で統計量と印刷版を混ぜない。**
   `trend` と `avgN` を混ぜたり、通常版と reverse holo を混ぜたりすると、
   市場の変動ではなくソース由来の段差がグラフに出ます。
   そのため `avg1/avg7/avg30` の**同一ファミリーのみ**で1系列を構成し、
   通常版が無い場合だけ reverse holo ファミリーに**まるごと**切り替えます。

⚠️ **既知の近似**: Cardmarket は EUR 建てのため USD に換算して保存しますが、
換算には**取得時点のレート**を使います。30日前の価格に今日のレートを当てるため
わずかな誤差が乗ります（カード価格の変動幅に対しては小さい）。
EUR を通貨として正式サポートすると `Currency` 型・`fx_rates`・表示層まで波及するため、
現時点では取り込み時換算としています。

また、履歴の書き込みは**スナップショットが0件のときだけ**実行します。
各点は実行時刻からの相対で打刻されるため、再実行すると微妙にずれた重複系列ができてしまいます。

| カテゴリ | ソース | 価格の性質 | 初期履歴 |
|---|---|---|---|
| トレカ（MTG） | Scryfall | **市場価格** ◎ | なし（前進蓄積のみ） |
| ポケモンカード | pokemontcg.io / Cardmarket | **市場価格** ◎ | **約30日分（3点）** |
| 遊戯王 | eBay Browse | 出品価格 △ | なし |
| 時計 | eBay Browse / 楽天市場 | 出品価格 △ | なし |
| スニーカー | eBay Browse / 楽天市場 | 出品価格 △ | なし |

**グラフが出るまでの期間はカテゴリで大きく異なります。**
ポケモンカードは初回 Cron の直後から約1か月分の線が出ますが、
それ以外は Cron が回るたびに1点ずつ増えるため、**線として見えるまで数日かかります**。
1〜8点しかない系列では点を明示表示して「まだデータが少ない」ことが分かるようにしています。

時計・スニーカー・バッグに**無料の「市場価格（実売）」API は存在しません**（§4 のとおり
StockX / Chrono24 に公開 API がない）。API から取れるのは出品価格までで、
実売価格は §8 のコミュニティ投稿から得る設計にしています。

### 7.5 ⚠️ 実地検証ができていない点

本調査は公式ドキュメントおよび公開情報に基づいていますが、
**ビルド環境のネットワークポリシーが `api.scryfall.com` と `api.pokemontcg.io` への
アクセスを遮断しているため、レスポンスの JSON 構造を実地で確認できていません。**

そのため両クライアントは**防御的にパース**しています。想定と異なる構造が返った場合、
例外や誤った数値ではなく `null`（＝「データ不足」表示）になります。
**本番の環境変数を設定した後、最初の Cron 実行結果を必ず確認してください：**

```bash
curl -H "Authorization: Bearer $CRON_SECRET" https://<本番ドメイン>/api/cron/refresh-prices
# {"ok":true,"updated":N,...} の N が 0 のままなら、パース側の調整が必要です
```

## 8. 実売価格の確保（2026-08-04）— 日本の中古相場とコミュニティ投稿

「市場価格 API がない部分の代替策」という指示を受けての調査と設計。
**結論を先に書くと、日本のオークション/フリマから実売価格を自動取得する手段は
無料・合法の範囲では存在しません。** そのため代替を2段構えにしました。

### 8.1 日本のマーケットプレイス API — 1つだけ採用

| サービス | 公開 API | 実売価格 | 判定 |
|---|---|---|---|
| **楽天市場（楽天ウェブサービス）** | ✅ 無料・即時発行 | ❌ 出品価格のみ | ✅ **採用** |
| Yahoo!ショッピング | ✅ 無料 | ❌ 出品価格のみ | 楽天と重複のため見送り |
| **ヤフオク!** | ❌ 一般開発者向けの検索 API は提供終了 | — | ❌ 使用不可 |
| **メルカリ** | ❌ 公開 API なし。規約でスクレイピング禁止 | — | ❌ 使用不可 |
| 駿河屋・magi 等 | ❌ 公開 API なし | — | ❌ 使用不可 |

**採用したのは楽天市場のみです。** 時計・バッグ・スニーカーの中古出品を
**JPY 建て**で取得できるため、USD 建ての eBay より日本の相場に近い数字になります。
実装は `apps/web/lib/sources/rakuten.ts`、環境変数は `RAKUTEN_APPLICATION_ID`。

⚠️ **これも「出品価格」であって落札価格ではありません。** eBay Browse と同じ性質で、
実際の成約より高く出ます。外れ値除去済み中央値を取る点も同じです。

⚠️ **義務**: 楽天ウェブサービスの規約により、データを表示する箇所に
出典表示が必要です。`sourceLabel()` が文言を持ち、銘柄詳細画面が表示します。

**なぜ「ヤフオク!の落札相場」を使わないのか。** 落札価格はまさに欲しいデータですが、
検索 API が一般提供されておらず、画面のスクレイピングは規約違反かつ
SPEC の完了条件（スクレイピング0行）に反します。**採用できません。**

### 8.2 利用者の売却実績 — Layer 3 の実装

§1 で「実際に売れた価格を持っているのはユーザーが自分で入力したアプリだけになる」と
書いた層を、蓄積のみから**実際の相場表示**に進めました。

**なぜ `transactions` を流用しないのか。**
ユーザーが取引履歴に入力した金額は RLS で保護された**私的な帳簿**です。
これを本人の同意なく公開集計に転用するのは、提供されていないものを公開する行為であり、
PDPA / GDPR の観点でも問題になります。したがって
**別テーブル `price_reports` への明示的な投稿**としました（マイグレーション 0006）。

**操作耐性のための3つのルール**（すべて DB 側で強制）

1. **1人1票。** 同一ユーザーの複数投稿はまず本人の中央値に畳んでから全体の中央値を取ります。
   20件投稿しても1件と同じ重みにしかなりません。
2. **投稿者3人未満は非公開。** それ未満は相場ではなく個別事例です。
   関数は行を返さず、UI は「まだ公開できる実績がない」と明示します。
3. **180日の窓。** 2年前の売却は今日の相場の根拠になりません。

**プライバシー**: 個別の投稿行は他人から一切読めません（RLS）。
公開されるのは集計値のみで、チャートの月次点も**3人以上いる月だけ**描画します。
1件しかない月を描くと、そこから個人の取引を逆算できてしまうためです。

**信頼度は最大でも "medium" に固定**しています（`communityConfidence()`）。
何人集まろうと自己申告データであり、集計済み市場フィードと同列に "high" とは呼べません。

### 8.3 可視化の方法

**出品価格と実売価格を1本の線にまとめてはいけません。** 出所も性質も違い、
平均すると「どのソースも言っていない数字」ができます。そのため:

| 系列 | 描画 | 意味 |
|---|---|---|
| 出品価格（API） | **実線** + 青 | 日次。今いくらで売られているか |
| 実売価格（投稿） | **破線** + 緑 + 常に点を表示 | 月次。実際にいくらで売れたか |
| 売買マーカー | B / S の丸 | 利用者自身の取引 |

実売系列を**常に破線かつ点付き**にしているのは、月次集計が本質的に疎だからです。
実線でつなぐと、報告のない日々にも観測があったように見えてしまいます。

### 8.4 投稿インセンティブの設計

**採用した方式: 貢献の可視化**（マイページに表示）

| 指標 | 意味 |
|---|---|
| 登録件数 | 投稿した実績の総数 |
| 登録した銘柄数 | カバーした銘柄の数 |
| **相場公開に貢献した銘柄数** | 自分の投稿が実際に**公開相場の一部になった**銘柄数 |

3つめが要です。「投稿したら他の人の役に立った」が事実として見えなければ、
投稿する理由になりません。

**検討したが採用しなかった方式: 相互性ゲート（投稿しないと相場を見られない）**

Glassdoor や levels.fyi が採る方式で、フリーライドを防ぐ効果は確実にあります。
採用しなかった理由は2つです。

1. **App Store / Google Play の審査リスク。** 主要機能を条件付きで隠す設計は
   審査で説明を求められやすく、初回提出のリスクを上げます。
2. **今回の目的と逆行する。** 現状の課題は「価格が表示されない」ことであり、
   ゲートは表示される場面をさらに減らします。

利用者が増えて投稿の質より量が問題になった段階で、
`community_price()` の呼び出し側にゲートを足せば導入できます（DB 側の変更は不要）。

### 8.5 ⚠️ 実地検証ができていない点

楽天ウェブサービスも**ビルド環境のネットワークポリシーで遮断**されており、
レスポンス構造を実地確認できていません。`rakuten.ts` は防御的にパースし、
想定外の構造では `null`（＝データ不足）を返します。
`lib/sources/rakuten.test.ts` に記録済みの構造でテストを固定しています。

コミュニティ集計は SQL 関数のため、**マイグレーション 0006 を適用した本番でのみ検証可能**です。
投稿3件（別アカウント3つ）を入れて初めて数字が出ます。

## 9. 高級車カテゴリ、カタログの拡充、ユーザーによる銘柄追加（2026-08-08）

### 9.1 高級車の価格ソース調査

無料で使える中古車相場 API を調べましたが、**専用の無料 API は存在しません。**

| サービス | 状況 |
|---|---|
| KBB（Kelley Blue Book） | API は法人向け商用契約のみ |
| Edmunds | API は法人パートナー向け、個人利用不可 |
| Autotrader / cars.com | 公開 API なし |
| CarGurus | 公開 API なし |
| グーネット・カーセンサー（国内） | 公開 API なし |

**結論**: 既存の eBay Browse API（eBay Motors）が、この製品が持つ唯一の無料手段です。時計・スニーカーと同じ仕組みで、`car` カテゴリの銘柄を eBay の出品価格（トリム済み中央値）で取得します。

⚠️ **時計・スニーカーより誤差が大きくなります。** eBay Motors の検索結果には、車両本体だけでなくパーツ・ミニカー・修理歴車が混在しやすく、キーワード検索の絞り込みだけでは除去しきれません。中央値を使うトリム処理（`trimmedMedian`、上下10%除去・最低5件）は同じ仕組みですが、車の場合はこのノイズに対する耐性がより試されます。実運用で明らかに異常な価格が出た場合は `search_query` の絞り込みを見直してください。

### 9.2 ユーザーによる銘柄追加

**設計判断**: `market_items` への書き込みは元々 service_role 限定（0001）です。管理者の価格登録（0003 `admin_set_price`）と同じ **SECURITY DEFINER 関数**のパターンを踏襲し、`create_market_item` 関数を追加しました。これにより、一般ユーザーの操作を許可しつつ `current_price` を直接書き換える経路にはなりません。

**カテゴリごとの自動ソース振り分け**:

| カテゴリ | ソース | 理由 |
|---|---|---|
| ポケモンカード | pokemontcg.io | 完全一致検索が可能 |
| トレカ（MTG想定） | Scryfall | 名称の完全一致検索 |
| 時計・スニーカー・車 | eBay Browse | 唯一の汎用ソース |
| バッグ | eBay Browse | 楽天より在庫が厚いと判断 |

**Scryfall に一致しないカード（遊戯王など）を追加した場合**: エラーにはなりません。次回の cron 実行で `insufficient`（データ不足）と判定され、0007 で実装した自己申告評価額の入力対象になります。失敗ではなく、既存の「データ不足→自己申告で補う」という設計にそのまま合流します。

### 9.3 検索のバイリンガル対応

既存のカタログは英語表記のみ（`Hermès`、`Chanel` 等）だったため、日本語での検索（「エルメス」「シャネル」）が一件もヒットしていませんでした。`market_items` に `aliases`（別名・別表記、空白区切りの自由記述）列を追加し、検索の `ILIKE` 対象に加えました。既存のバッグ10件と新規追加分すべてに日本語別名を設定しています。

### 9.4 カタログの拡充

バッグ16件・高級車14件を追加しました（migration `0009`）。デフォルト表示件数の上限も 60→200 に引き上げています（現状のカタログ規模（約84件）であれば全件が一覧に収まります）。

## 10. 売却性（日本・シンガポール）の改善（2026-08-08）

買い手が最初に見るのは「どれだけ人が来ていて、どれだけ増えているか」です。

## 13. 競合調査：日本のトレカ資産管理アプリ（2026-08-11）

### 13.1 調査の制約 — 先に明記する

**mycafolio.com、pokeca-chart.com、tcgdex.dev はいずれもビルドサンドボックスの
egress ポリシーによりブロックされており、直接アクセスして通信内容を確認できていない。**
以下は検索結果からの再構成であり、「このアプリはこの API を使っている」と
断定できた項目は一つもない。断定的に書かないのはそのためである。

### 13.2 結論：日本のトレカ相場に「公式 API」は存在しない

調べた範囲では、日本語のトレカ相場を JPY で配信する公式・無料の API は無い。
実在するのは次の2層で、**両者はまったく別物**である。

| 層 | 内容 | 入手手段 | 我々の状況 |
|---|---|---|---|
| カード原簿（名前・画像・セット・レアリティ） | 静的マスタ | 公式 API あり（無料） | ✅ 利用中 |
| 日本の実勢価格（JPY） | 販売価格・買取価格 | **公式 API 無し。各ショップのスクレイピング** | ⚠️ 未対応 |

**カード原簿の入手先（いずれも商用可・画像配信あり）**
- `pokemontcg.io` — ポケモン。TCGplayer(USD) / Cardmarket(EUR) 価格を同梱。**現在利用中**
- `Scryfall` — MTG。**現在利用中**
- `TCGdex` — API キー不要、日本語カードを収録。**未検証だが有力な補完候補**

**日本の実勢価格の実態**
検索で繰り返し現れたのは、カードラッシュ・遊々亭・駿河屋・magi・トレトク・
CARDMAX・メルカリといった**ショップ横断のスクレイピング**である。
ココナラ／ランサーズで「ポケカ販売価格を毎日自動で蓄積しグラフ化」する
ツールが商品として販売されている事実が、これが業界標準の手段であることを示す。
駿河屋の公式 API は見つからず、非公式のスクレイピングライブラリのみが存在した。

なお DMMマイカ（旧 Mycalinks / myca.cards）は DMM が自社 EC を運営しているため、
**一次取引データを持つ**。これは外部から模倣できない構造的優位であり、
「同じ土俵で価格精度を競わない」という判断の根拠になる。

### 13.3 スクレイピングを採用しない判断

技術的には可能だが、以下の理由で**現時点では採らない**。

1. **売却時に負債になる。** 買い手のデューデリで「主要データが第三者サイトの
   規約違反スクレイピングに依存」と判明した場合、価格に直接響く。
   §10 で積み上げてきた譲渡可能性の議論と正面から衝突する。
2. **各社の利用規約で禁止されている場合が多い。**
3. **壊れ方が静か。** HTML 構造の変更で無言のうちに間違った価格が入り、
   本 App が最も重視してきた「価格の信ぴょう性」を根本から損なう。

代替として、§8 で設計済みの**コミュニティ投稿による実売価格**を伸ばす方が、
規約上も売却上も安全であり、かつ自社データ資産として積み上がる。

### 13.4 採用した点：入力時に画像と価格を出す

競合が明確に優れていたのは価格の精度ではなく **入力体験** である。
名前を打つと、**画像と現在価格が付いた候補**が出て、そこから選ぶだけで登録が終わる。

これを本 App にも入れた（migration 0014）。
- `market_items.image_url` を追加
- 日次バッチが**価格と同じレスポンスから**画像を拾って保存（追加リクエストゼロ）
  - Scryfall → `image_uris.normal`、pokemontcg.io → `images.small`
- 銘柄追加フォームの候補一覧に「画像・名前・現在価格」を表示
- Browse 一覧・銘柄詳細・ポートフォリオ一覧にも反映（Web / アプリ両方）

**画像はカードのみ。** 時計・バッグ・スニーカー・車は従来どおりカテゴリー
グリフのままとする。これらの価格元は eBay と楽天であり、そこにある画像は
**出品者が自分の商品を撮った写真**で、再配布する権利が我々に無い。
高級ブランドでは商標上の問題にも直結する。カード画像は事情が異なり、
Scryfall と pokemontcg.io が**コレクション管理ソフトでの表示を想定して**
配信しており、両者とも銘柄画面で出典表示済みである。

### 13.5 未実装だが検討に値する点

- **PSA 等の鑑定品を別銘柄として扱う。** 鑑定の有無で価格帯が桁違いになるため、
  本来は同一銘柄で持つべきではない。データモデルの課題。
- **未開封 BOX / パックのカテゴリ追加。** 日本では主要な投資対象。
- **銘柄ごとの増減率表示。** 現状は合計のみ。実装コストは小さい。
  （「ROI」「リターン」等の投資用語は、金商法上の誤認を避けるため使用しない）
- **TCGdex による日本語カードの補完。** API キー不要。要検証（§13.1）。

## 14. マネタイズ設計（2026-08-11）

### 14.1 調査の制約

**mycafolio.com / myca.cards はいずれも egress ポリシーによりブロックされており、
利用規約・プライバシーポリシーを読むことができなかった。**
以下の設計は、提供されたプラン画面のスクリーンショット1枚と §13 の調査に基づく。
競合の規約から得た情報は含まれていない。

### 14.2 競合のプラン構成（スクリーンショットから読み取れた範囲）

| 項目 | 内容 |
|---|---|
| 無料プラン | 登録枚数 **30枚** まで |
| 有料プラン | **¥980 / 月**（カード登録無制限・広告なし・iCloudバックアップ） |
| 都度購入 | **¥800** で登録枠 +100枚（買い切り） |
| 課金基盤 | Apple ID（App Store 課金）、「購入を復元する」あり |
| データ保存 | 端末内。プレミアムのみ iCloud バックアップ |

**重要な観察**: 課金対象が「機能」ではなく **登録枚数** である。
広告除去は付随的で、主たる価値は枠の拡張にある。

### 14.3 本 App の設計

| 項目 | 内容 |
|---|---|
| 無料プラン | **20件** まで |
| 無制限プラン | **¥500 買い切り**（月額なし） |
| 制限対象 | 登録件数のみ |
| 制限しないもの | 価格・グラフ・出典表示・履歴・カテゴリ ― **すべて無料と同一** |

**20件にした理由**: 競合の30枚はカード専用アプリの数字である。本 App は時計・
バッグ・車を含むため、コレクションは「枚」ではなく「点」で数えられ、桁が一つ小さい。
20 はライトユーザーが一生到達しない一方、対象顧客は数ヶ月で到達する。

**機能ではなく件数で区切る理由（3つ）**
1. 価値と連動する。4件しか登録していない人は対価を払うほどの価値を得ていない。
2. **プロダクトを劣化させる動機が生まれない。** 「正確な価格」を有料にすると、
   無料版をわざと悪くする理由ができる。数字の正確さが本 App の全価値なので、
   この動機を構造的に排除する。
3. **Scryfall のライセンスは、そのデータを有料の壁の内側に置くことを禁じている**
   （§7）。機能課金は規約違反になる。件数制限は違反しない。

### 14.4 実装（migration 0015）

- `entitlements` テーブル。**行が無い = 無料** とし、無料用の行を作らない
- `expires_at` が **NULL = 買い切り / 日時 = サブスク**。
  スキーマ変更なしで両方の商品形態を表現できる（価格戦略の変更をマイグレーション
  無しで行えるようにするため）
- **上限は DB のトリガーで強制する。** ネイティブアプリは PostgREST に直接
  書き込むため、UI 側のチェックだけでは curl と anon key で迂回できる。
  migration 0004 の数量トリガーと同じ理由
- `entitlements` に **insert/update/delete の RLS ポリシーを一切置いていない**。
  クライアントが書けるなら自分に無料で有料プランを付与できてしまう
- `grant_unlimited()` は `is_admin()` を関数内で再チェックし、`receipt_id` で
  冪等。ストアは webhook を再送するため

### 14.5 未実装：決済プロバイダ

**決済は接続していない。** 購入ボタンは意図的に置いていない。
決済できないボタンは、意思を受け取ってから失敗するため、無いより悪い。

接続時の手順は次のとおり:
1. サーバー側でレシートを検証（Apple / Google / Stripe）
2. **検証後に** `grant_unlimited(user_id, provider, receipt_id, expires_at)` を
   service role で呼ぶ
3. `/plan` の「決済は準備中です」ブロックを購入ボタンに差し替える

⚠️ **iOS ではアプリ内デジタルコンテンツの販売に App内課金（IAP）が必須**であり、
Apple の手数料が発生する。Web 側は Stripe を使えるため手数料が低い。
両方を用意し、Web で購入した権利がアプリでも有効になる設計（＝サーバー側で
entitlement を保持する今の形）が、手数料と体験の両面で有利。

### 14.6 売却性への影響

買い切り ¥500 は導入障壁が低く初速は出るが、**MRR が積み上がらない**ため
評価倍率は付きにくい。売却を優先するなら月額への変更を検討する価値がある。
`expires_at` を使えばマイグレーション無しで切り替えられるようにしてあるのは
このためである。
