## 1. サービス概要

**Oh My Asset** — コレクション資産（カード・時計・バッグ・スニーカー・車）の
保有記録と推定市場価値の追跡。対象市場は日本とシンガポール。

- 無料プラン: 10件まで登録可
- 有料プラン: 月額 ¥500 / 年額 ¥5,000（無制限）
- 収益モデル: 継続課金のみ。広告・データ販売は行っていない

**法的立ち位置**: 投資助言ではなく記録ツール。金融商品取引法に該当しない旨を
利用規約に明記。表示価格は「推定値」であり実売価格を保証しない。

### コード構成

```
oh-my-asset/
├── apps/web/            Next.js 本体（これがデプロイされる）
│   ├── app/             ルーティング。ディレクトリ = URL
│   ├── lib/             外部API・Supabaseクライアント・Stripe
│   └── components/      共通UI
├── apps/mobile/         Expo (React Native)。未公開
├── packages/core/       Web/モバイル共通ロジック（計算・i18n・型）
└── supabase/migrations/ 0001〜0028。番号順に実行する
```

**重要な設計原則**（改修時に壊さないこと）:

1. **`market_items` には認証ユーザー向けのWRITE用RLSポリシーが無い。**
   これは意図的です。価格の書き込みは全て `SECURITY DEFINER` 関数経由。
   クライアントのフォームが `current_price` を偽造できないようにするため。
2. **管理者用関数は関数の内部で `is_admin()` を再チェックする。**
   ページ側のチェックは表示制御のためだけ。Server Actionはページを描画せず
   到達可能なため。
3. **`SECURITY DEFINER` 関数は必ず `set search_path` を指定する。**
4. **価格の下限・上限（band）はアイテムの通貨で保存される。**
   別通貨のソースと比較する際は必ず換算する（`convertBand`）。

## 4. 運用手順

### 日次（自動・人手不要）

`/api/cron/refresh-prices` が毎日 05:00 JST に自動実行されます。
- 価格の更新（1回あたり最大50銘柄）
- 指標スナップショットの記録（`daily_metrics`）

**確認方法**: Vercel → Deployments → Functions → Cron のログ。
レスポンスJSONの `updated` / `insufficient` / `failed` / `metrics` を見る。

### 週次（5分）

1. **管理画面 `/admin` を開く**（管理者アカウントでログイン時のみメニューに表示）
2. **承認待ちアイテム**を処理（ユーザーが追加した銘柄の公開可否）
3. **価格の根拠**パネルで、判定理由が `too_few` / `no_listings` の銘柄を確認
   - 検索リンクを開いて実際の出品を見る
   - 検索語や価格帯を修正して再承認
4. **表記ゆれ・重複アイテム**があれば統合
5. **問い合わせ**の未対応を処理

### 月次（15分）

1. `/admin` の**売上（月次）**を確認し、Stripeダッシュボードと突合
2. `/admin/export?type=revenue` でCSVを保存（会計証跡）
3. `/admin/export?type=metrics` でCSVを保存（指標の月次バックアップ）
4. Supabase の使用量（DB容量）を確認

### 価格データを手動で更新したいとき

`/admin` の「価格を更新」ボタン。`CRON_SECRET` はサーバー側にしか無いため、
サーバーアクション経由で呼び出されます。

## 5. 障害対応

| 症状 | 原因の可能性 | 対処 |
|---|---|---|
| 価格が全て「データ不足」 | APIキー失効／価格帯が狭すぎ | `/admin` の「価格の根拠」で判定理由を確認 |
| 新規登録でメールが届かない | Brevo送信上限／ドメイン認証切れ | Supabase → Auth → SMTP設定を確認 |
| 課金されるが権限が付かない | Stripe webhook の署名不一致 | Stripe → Developers → Webhooks でエラーを確認。`STRIPE_WEBHOOK_SECRET` を再設定 |
| cronが動かない | Vercelのプラン変更／`CRON_SECRET` 不一致 | Vercel → Settings → Cron Jobs |
| 特定ユーザーだけ課金が反映されない | `metadata.user_id` の欠落 | Stripe の該当subscriptionのmetadataを確認。手動で `grant_subscription` を実行 |

### 緊急時の手動操作（Supabase SQL Editor）

```sql
-- 特定ユーザーに無償で権限を付与
select public.grant_unlimited(
  '<user-uuid>', 'admin', null, null, '手動付与の理由'
);

-- 権限を剥奪
select public.revoke_unlimited('<user-uuid>');

-- 指標を手動で記録（cronが失敗した日）
select public.capture_daily_metrics();
```

## 6. 譲渡にあたって必要な作業

> **ここが商品価値に直結します。** 「引き継げない要素」が1つでもあると
> 買い手は減額を要求します。以下を事前に潰しておいてください。

### 6-1. APIキーの扱い ⚠️ 最重要

**結論: このサービスのAPIキーは「譲渡」する必要がありません。**

すべての外部APIキーは**環境変数として注入**される設計で、コードには一切
埋め込まれていません（`apps/web/.env.example` 参照）。したがって譲渡時は:

**買い手が自分名義で新しいキーを取得し、Vercelの環境変数を差し替えるだけ**で
完全に動作します。売り手のキーを引き渡す必要も、名義変更を申請する必要も
ありません。

これは「譲渡可否が不明」というリスクを**設計で回避している**状態です。
買い手への説明としてはこう言えます:

> 「APIキーは譲渡しません。買い手様ご自身の名義で無料登録いただき、
> 環境変数を差し替えてください。所要時間は30分程度です。」

**各APIの取得可否（買い手が自分で取れるか）**:

| API | 取得条件 | 商用利用 | 確認すべき条項 |
|---|---|---|---|
| Rakuten Web Service | 楽天会員なら即時発行・無料 | 可 | 「楽天ウェブサービス利用規約」の商用利用条項、**Rakuten Web Serviceへの帰属表示義務**（実装済） |
| eBay Browse API | eBay開発者登録・無料 | 可 | eBay API License Agreement。Browse APIは制限スコープ不要 |
| Scryfall | 登録不要 | 可 | **データの有料化を禁止**（実装済: 価格を有料プランに閉じ込めていない） |
| Pokémon TCG API | 無料登録でキー発行 | 可 | レート制限 |
| open.er-api.com | 登録不要 | 可 | — |

> **⚠️ 私はこの環境から外部ネットワークに接続できないため、上記の規約原文を
> 直接確認できていません。** 譲渡契約の前に、買い手と共に各規約の最新版を
> 確認してください。特に確認すべきは「アカウントの譲渡禁止条項の有無」ですが、
> **上記のとおり譲渡しない設計なので、実務上の争点は「買い手が自分で取得
> できるか」だけ**になります。いずれも無料・即時発行のため、リスクは低いと
> 評価できます。

## 7. 数字の出どころ（買い手からの質問に答えるため）

| 指標 | 出どころ | 注意 |
|---|---|---|
| 会員数 | `auth.users` | Supabaseの認証テーブル |
| MAU | `daily_metrics.active_30d` | **取引を記録したユーザー数**。ログインだけの人は含まない（意図的：この製品の「利用」は記録すること） |
| 有料会員数 | `daily_metrics.paying_total` | `status='active'` かつ未失効 |
| MRR | `daily_metrics.mrr_jpy` | 年額は1/12して計上。支払月に12ヶ月分を計上しない |
| 売上 | `revenue_events` | Stripeのwebhookから記帳。手数料は `balance_transactions` から実額を取得 |
| 追跡中アイテム数 | `holdings` | トップページで公開している数値 |

**重要**: `daily_metrics` は**記録を開始した日より前に遡れません**。
MAUや継続率は時系列でしか表現できず、現在の状態しか持たないデータベースから
過去を再構成することは不可能です。マイグレーション0028を適用した日が
指標の開始日になります。**適用が早いほど、売却時に見せられる履歴が長くなります。**
